# 기본 XP 정수 ID 테이블 순서

> 독립 소스 저장소 안내: 아래의 이전 DLL 해시·build 경로는 분리 전 검증 기록입니다.
> 원시 자료는 포함하지 않으며, 새 저장소의 실제 빌드·검사 결과는 [VALIDATION.md](../VALIDATION.md)에 구분합니다.

Ruby 4의 Hash는 삽입 순서로 순회합니다. 원본 RGSS의 32비트 Ruby 1.8 Hash는
다른 순서이며, 이는 겹친 이벤트 중 먼저 선택되는 이벤트와 병렬 이벤트의 최종 결과에 영향을 줍니다.
ID 1~10을 순서대로 넣었을 때 원본의 키 순서는 `5,6,1,7,2,8,3,9,4,10`입니다.

`src/runtime/integer_map.rb`는 기본 Game_Map의 이벤트·공통 이벤트와
Game_Battler/Game_Actor의 상태 턴 테이블에 한정해 이 순서를 구현합니다.
기본 스크립트 변환기에 정확한 소스 해시를 확인하는 규칙을 추가했습니다.
저장 관련 변경과 합해 90개 중 8개 엔트리를 변경하고 나머지 82개의 원시 바이트는 보존합니다.
변경 위치와 전후 소스는 각 복사본의 `migration/`에서 확인할 수 있습니다.

원본 데이터의 Hash는 Ruby 4가 보존한 Marshal의 pair 순서로 재구성합니다.
원본 세이브는 Scene_Load에서 관련 ID 테이블을 같은 규칙으로 복원합니다.
새 엔진 저장은 ID 테이블의 현재 순서·용량을 자체 Marshal 표현으로 보존합니다.
객체 공유와 순환 참조도 유지합니다. 원본 세이브에는 쓰지 않습니다.

이 클래스는 Hash의 하위 클래스이며 기본 스크립트가 사용하는 조회·대입·삭제·순회만 지원합니다.
정수 키는 원본 32비트 Fixnum 범위로 제한하며, 미지원 변경 메서드는 오류를 냅니다.
일반 Ruby Hash 전체, 사용자 플러그인의 순회 중 삽입 동작, Bignum·문자열 키 해시까지
Ruby 1.8과 같다고 주장하지 않습니다. 일반 Ruby 4 Hash는 변경하지 않습니다.

## 근거와 재현

직접 만든 시험 코드로 원본을 실행해 다음을 비교했습니다.

- 0~999개 ID, 정방향/역방향 삽입, 여러 재해시 경계, 치환·삭제·재삽입·복사·clear,
  음수 및 경계 Fixnum: 230개 순서 기록 일치.
- 실제 기본 Game_Map/Interpreter: 10/12/66/67/100/300개의 겹친 이벤트,
  결정키·접촉 이벤트 선택, 병렬 이벤트·공통 이벤트의 결과, 원본 세이브 가져오기: 33개 기록 일치.
- 새 저장에서 재해시 후 삭제된 테이블의 순서·용량, 값의 공유와 자기 참조 보존.
  frozen·미지원 키/변경 메서드·잘못된 저장 구조 거부 검사.

```powershell
python scripts/test_runtime_order.py System RGSS104E.dll build/runtime-native/bin/Release/RGSS104E.dll build/order-check
```

현재 개별 근거는 `build/runtime-integer-order-check-3/`에 있습니다.
원본 스크립트 정의·로컬 세이브·게임 데이터가 포함된 원시 시험 출력은 공개하지 않습니다.
알고리즘 확인용으로 [공식 Ruby 1.8.1 소스](https://cache.ruby-lang.org/pub/ruby/1.8/)의
Hash/st 규칙도 읽었습니다. 참고 tarball SHA-256은
`d0f1e19fc7a14233ed0e1335867f7a7ddb18b85ab4c58795c5fc5a562710de4e`입니다.
Ruby 1.8은 엔진에 빌드하거나 연결하지 않았으며 런타임은 계속 Ruby 4.0.7 x86입니다.
