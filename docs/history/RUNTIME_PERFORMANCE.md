# 자체 엔진 성능 측정

> 독립 소스 저장소 안내: 아래의 이전 DLL 해시·build 경로는 분리 전 검증 기록입니다.
> 원시 자료는 포함하지 않으며, 새 저장소의 실제 빌드·검사 결과는 [VALIDATION.md](../VALIDATION.md)에 구분합니다.

원본 Game.exe, 원본 RGSS와 자체 엔진을 프로젝트 복사본에서 비교합니다.
이 문서의 자체 엔진은 Ruby 4.0.7 x86, 640×480, 40Hz입니다.
기존 보조 DLL의 성능 결과와 구분합니다. 원본 파일과 시스템 타이머·우선순위는 바꾸지 않습니다.

## 측정 방법

`scripts/benchmark_runtime.py`는 원본 스크립트 정의와 명시적으로 변환한 정의를 사용합니다.
직접 생성한 40×30 맵·이미지에서 플레이어, 맵, 인터프리터, 스프라이트를 실제로 갱신합니다.
네 장면은 이벤트 0개, 정지 100개, 정지 300개, 경로 이동 300개입니다.
100/300개 장면에는 각각 병렬 이벤트 10/30개가 포함됩니다.
플레이어의 논리 입력은 같으며 게임 속도를 올리거나 화면 갱신을 생략하지 않습니다.

각 장면은 80프레임을 워밍업하고 400프레임을 수집합니다. 원본/자체 실행 순서를 번갈아
3쌍 측정합니다. 각 쌍의 플레이어·이벤트 위치/방향/패턴, 타이머, 병렬 이벤트 결과가 같아야 합니다.
프레임 시작/종료의 포커스 검사에 실패한 실행은 제외해 재사용하지 않고 실패로 처리합니다.
실제 실행 모듈 해시로 원본/보조 DLL의 혼입 여부를 검사합니다.

- 프레임 간격: 연속한 `Graphics.update` 완료 사이의 QPC 시간. p50/p95/p99와
  37.5ms/50ms 초과 횟수를 함께 보고합니다. 첫 프레임은 해당 프레임 시작을 기준으로 합니다.
  모니터에 실제 표시된 시각이나 입력부터 표시까지의 지연을 측정한 값은 아닙니다.
- CPU: `GetThreadTimes`와 `GetProcessTimes`의 차이. 개별 프레임 값은 양자화되어 있으므로
  장면 평균만 비교합니다. 그래픽 구간 wall 시간에는 대기가 포함되어 CPU 시간과 다릅니다.
- 계측: 별도 `RGSSBenchMetrics.dll`의 QPC/CPU/포커스 스냅샷. 기본 비교 실행에서는
  엔진 내부 주소·IAT·GC·대기 정책을 수정하지 않습니다. 3,000회 빈 반복 대비 계측 3회 호출의 비용을 기록합니다.
- GPU timestamp: 자체 D3D11 엔진만 별도 실행에서 수집합니다. 완료된 렌더 시퀀스로 중복을
  제거하고, disjoint/미완료 결과를 유효한 시간으로 만들지 않습니다. 원본 GPU 시간과의 직접 비교가 아닙니다.
- GPU Engine: `profile_runtime_gpu.py`의 별도 PID별 PDH 수집. 원본 DirectDraw도 관찰하며
  Running Time과 utilization raw numerator의 단위를 대조합니다. 워밍업·장면 경계를 건너는
  구간, 초기/초기화된 인스턴스와 사라진 인스턴스의 미관측 꼬리는 보간하지 않습니다.
  두 numerator가 일치하지 않는 표본과 그 다음 구간은 미확정으로 제외하며 허용 오차로 통과시키지 않습니다.
  실제 provider의 counter type과 10,000,000Hz time base도 검사합니다.
  여러 엔진의 작업 시간은 겹칠 수 있어 합계가 프레임 GPU 시간이나 표시 지연을 뜻하지 않습니다.
- 렌더 세부 구간: `profile_runtime_render.py`에서 동일 update의 Ruby 명령 생성,
  native 제출, 프레임 대기를 분리합니다. 이 추가 계측 실행은 기본 프레임 비교에 섞지 않습니다.
- 원본 대기: `profile_original_wait.py`의 별도 관측. 고정된 원본 해시와 호출 바이트·IAT 대상만
  허용하고, 실제 1ms 프레임 대기의 인자와 반환값을 그대로 전달합니다. GC/타이머 정책은 바꾸지 않으며
  종료 후 원래 IAT를 복구하고 재연결로 확인합니다. 이 관측의 QPC 오버헤드가 포함됩니다.
  원본 파일을 수정하거나 관측 코드를 게임 배포 DLL에 넣지 않습니다.

## 확인한 병목과 변경

첫 3쌍(`build/runtime-benchmark-pairs-1/`, 자체 DLL
`bd75859992990f0c6036b656922e3ce26e4aa850a878c55859a4fcae4b428f90`)에서는
이동 300개 장면의 p95가 개선돼도 37.5ms 초과 프레임이 원본 3개 대비 자체 27개였습니다.
그 프레임의 로직 구간은 약 32~74ms로, 렌더 제출보다 로직의 꼬리가 문제였습니다.

별도 진단에서 정수 ID 순서 호환 테이블의 `values` 재구성 비용을 확인했습니다.
호환 순서가 변하지 않으면 내부 값 배열을 재사용하고, 호출자에게는 새 얕은 복사본을 반환하도록
수정했습니다. 대입·치환·삭제·clear·복사·로드 때 무효화합니다. 기존 사용자에게 돌려준 배열,
객체 공유·순환 참조, frozen 읽기, 기존 순서와 저장 payload는 유지합니다.
230개 원본 ID 순서와 33개 이벤트 결과, 캐시 무효화 검사를 다시 통과했습니다.

렌더 진단의 명령 생성 평균은 장면별 약 2.06/2.84/4.52/4.56ms였습니다.
표시 속성 getter/setter가 호출마다 필드명 문자열을 만드는 비용도 제거했습니다.
동일 getter 10만 회의 분리 검사에서 할당 수는 100,015개에서 15개로 줄었습니다.
이는 게임 전체의 속도 향상률이 아닙니다. 해제된 객체의 오류와 속성별 값/형 변환은 유지합니다.

최신 측정 결과와 해시는 아래 검증 기록을 기준으로 판단합니다. p95와 긴 프레임,
CPU·GPU·대기는 서로 다른 지표이며 하나의 개선으로 나머지의 개선을 주장하지 않습니다.

## 재현

빌드 및 전체 회귀 검사를 먼저 실행합니다. 관측 DLL은 게임에 배포하지 않습니다.
테스트 중 게임 창이 활성 상태여야 하며 화면 캡처/다른 게임 실행을 섞지 않습니다.

```powershell
cmake --build build/runtime-native --config Release --target RGSSBenchMetrics RGSSWaitObserver
python scripts/benchmark_runtime.py System RGSS104E.dll build/runtime-native/bin/Release/RGSS104E.dll build/bench --frames 400 --pairs 3 --gpu-diagnostic
python scripts/summarize_runtime_bench.py build/bench build/bench/comparison.json
python scripts/profile_runtime_render.py System build/bench/fixture build/runtime-native/bin/Release/RGSS104E.dll build/render-parts
python scripts/profile_runtime_gpu.py System build/bench/fixture RGSS104E.dll build/runtime-native/bin/Release/RGSS104E.dll build/gpu-engines
python scripts/profile_original_wait.py System build/bench/fixture RGSS104E.dll build/original-wait
```

원시 출력에는 로컬 원본 스크립트·게임 데이터가 들어 있어 `build/`에만 보관합니다.
공개 문서에는 직접 만든 시험 코드와 집계 수치만 포함합니다.
같은 PC의 제한된 장면 결과이며 전체 화면·다른 GPU/드라이버·모든 게임의 성능을 보장하지 않습니다.

참고: [Microsoft의 GPU 스케줄러·프로세스별 엔진 지표 설명](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/),
[PDH counter type 조회](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhgetcounterinfow),
[PDH time base 조회](https://learn.microsoft.com/en-us/windows/win32/api/pdh/nf-pdh-pdhgetcountertimebase).

기본 성능 비교의 표본에 추가 계측 실행을 섞지 않습니다. 각 장면 400프레임씩 세 번의
원본/자체 대기, 자체 비동기 GPU timestamp 및 절대 QPC를 기록했습니다.
자체 GPU timestamp는 실제 측정 프레임과 연결한 유효 표본 384개씩을 사용하며,
ETW에서는 각 측정 프레임의 Present를 총 4,800개 연결했습니다.
원본 세 실행은 PresentMon 프레임 CSV가 없어 원본 GPU 비용과 GPU 개선율이 미확정입니다.
대기의 감소는 CPU 처리 비용 증가로도 발생하므로 성능 개선율로 해석하지 않습니다.
측정 구간·통계·원본 귀속 한계와 결과 표는 [GPU·대기 반복 측정](RUNTIME_GPU_TRACE.md)에 있습니다.
