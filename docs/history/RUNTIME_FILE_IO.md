# 파일 읽기 작업 분리

> 독립 소스 저장소 안내: 아래의 이전 DLL 해시·build 경로는 분리 전 검증 기록입니다.
> 원시 자료는 포함하지 않으며, 새 저장소의 실제 빌드·검사 결과는 [VALIDATION.md](../VALIDATION.md)에 구분합니다.

2026-10-18. 후보 DLL: `d51cbd7e2bc9bab619a1f9ea4c5222e1c8bac0cd388a9a3d83ca9f46e56853a7`.
원본 파일과 이전 후보는 보존했습니다. 새 파일 읽기 코드는 원본 RGSS를 호출하지 않습니다.

`file_io.cpp`는 UTF-8 경로·오프셋·길이·기대 파일 크기를 네이티브 값으로 복사한 뒤
`std::async(std::launch::async, ...)` 작업에서 파일을 열고 읽고 닫습니다.
작업 스레드는 Ruby API나 Ruby 객체의 메모리를 사용하지 않습니다.
반환 바이트를 Ruby String/Array로 만드는 부분은 호출 스레드의 `rb_protect` 안에 두었습니다.
Ruby 예외를 다시 던지기 전에 C++ 버퍼와 future를 해제합니다.

## 연결한 경로

- `RGSSXP.read_file`: 스크립트·데이터·이미지·오디오의 공통 내용 읽기.
- `Archive::Reader`: 기존 Ruby RGSSAD 파서에 64KiB 단위의 네이티브 읽기 버퍼를 제공합니다.
  항목 본문은 인덱스의 오프셋·길이·전체 크기를 확인해 별도로 읽습니다.
  기존 버전·이름·경계·중복·항목 수 검사와 키 계산은 유지합니다.
- `Saves.open_read`: Import 복사본과 새 저장을 네이티브에서 읽고, Ruby의 StringIO로
  기존 순차 Marshal 읽기 인터페이스를 제공합니다. 저장 위치·버전 표식·원자적 쓰기는 유지합니다.
  기본 저장/불러오기 화면이 쓰는 `mtime`은 Windows 파일 정보의 100ns 시각으로 제공합니다.
  같은 초 안의 저장 순서와 표시 시간대, 닫힌 스트림의 오류도 검사합니다.

StringIO 3.2.0은 이미 고정한 Ruby 4.0.7 배포 소스에 포함되어 있습니다.
소스 해시를 `ruby.lock.json`에 기록했고 CMake가 빌드 전에 확인합니다.
별도 gem 설치나 추가 DLL은 필요하지 않습니다. Ruby 라이선스를 따릅니다.
처음에는 확장 등록만 해서 세이브 관문에서 NameError가 발생했습니다(`runtime-verification-29`).
스크립트 실행 전에 등록된 확장을 require하도록 고쳤으며 검사를 완화하지 않았습니다.
이후 실제 저장 화면에서 `mtime` 누락도 확인했습니다(`runtime-stock-full-combat-8`).
필요한 읽기 인터페이스를 보충했고, 초 미만 시각까지 원본 File.mtime과 대조하는 회귀 검사를 추가했습니다.
`runtime-stringio-incremental-guard-1`은 별도 소스 복사본을 변경해 증분 빌드가 의도한
해시 오류로 거부되는지도 확인했습니다. 원래 제3자 소스는 바꾸지 않았습니다.

## 검사

```powershell
python scripts/test_runtime_file_io.py "LOCAL_ORIGINAL_GAME_EXE" build/runtime-native/bin/Release/RGSS104E.dll build/check-file-io
```

원본 실행기를 격리 복사본에서 사용합니다. 자기 생성 바이너리의 전체/구간/빈 읽기, 한글 경로,
네이티브 긴 경로, 파일 없음·잘못된 인자·NUL 경로, 128MiB 한계, 큰 파일의 작은 구간,
2,001개 RGSSAD 항목의 캐시 경계·seek·키 계산, 손상 헤더·잘못된 이름·중복·변경된 파일을 검사합니다.
네이티브 호출자/작업 스레드 ID와 실제 읽기 횟수도 기록합니다.
`runtime_saves.rb`는 Import와 새 저장 읽기가 작업 경로를 거쳤는지 별도로 확인합니다.
전체 회귀 도구에는 `file-io` 관문을 추가했습니다.

## 한계

호출은 읽기가 끝날 때까지 기다립니다. 게임 로직·렌더 진행 순서를 바꾸는 비동기 로딩이나
맵 로딩 속도 개선을 증명한 구현은 아닙니다. Ruby 경로 검색의 파일 정보 조회와 저장 쓰기는 주 스레드에 남습니다.
캐시 미스마다 네이티브 작업을 하나 만듭니다. 이 비용이 병목으로 측정되면 지속 작업 스레드로 바꿉니다.
한 번에 반환하는 내용은 128MiB까지이며, 큰 아카이브는 구간 읽기로 인덱싱합니다.
파일 크기 변경은 거부하지만 같은 크기로 동시에 바뀌는 내용의 원자적 스냅샷은 보장하지 않습니다.

네이티브 읽기는 확장 경로를 처리하지만, 현재 Ruby 자체의 일반 File/Dir 및 자산 검색에서
260자 초과 경로 전체를 지원한다고 주장하지 않습니다. 이 제한은 시험 도중 확인했습니다.
배율·Windows 설정은 시험하거나 변경하지 않았습니다.
이전 DLL의 성능·30분·물리 조작 결과를 이 후보의 새 실행 결과로 옮기지 않습니다.
